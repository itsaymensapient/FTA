How the agentic AI system works, and what you build

Seven detailed diagrams with reading notes. Start with the overall system, understand how instructions and evidence enter the workflow, trace a real scenario, and then follow the implementation sequence.

Your role as AI engineer: turn the scenario narrative into executable agent workflows with approved instructions, scoped tools, deterministic calculations, traceable explanations, controlled actions and measurable acceptance checks.

This is a proposed design based on the supplied draft, Ali’s feedback and Sulieman’s architecture. It does not establish approved ownership or confirmed platform capabilities. The scenario amounts are synthetic demonstration data.

The terms in everyday language
  • Supervisor: the coordinator that chooses tasks and collects results.
  • Specialist workflow: a focused task such as retrieving records or preparing an explanation; it does not require a separately trained model.
  • Tool: a controlled function the application runs to read records, calculate or submit an approved change.
  • Gold: the curated data tables the project has prepared for reliable queries.
  • Retrieval / RAG: finding relevant approved passages and giving them to the model as reference material.
  • Case state: a saved progress record of what was found, approved, submitted and still needs attention.
  • Idempotency key: a unique operation key that helps prevent a repeated request from making the same change twice.

These are concrete examples using the supplied synthetic demonstration draft, not live taxpayer transactions. Any tool behavior described is proposed application behavior to implement and verify.

1. Understand the complete system

Where does your work start and end?

Your main deliverable is the agent application: task instructions, planning, specialist workflows, tools, evidence handling, explanations and evaluation. Data engineers provide reliable records; domain owners approve rules; application engineers connect screens and operational APIs; the platform team provides the agreed Cloudera environment. These ownership boundaries are proposed for team agreement.

Follow the request from the visitor interface to the application, then down to the evidence and execution layers. Gold supplies curated analytical facts. Case state and operational submission status need their own persistent records and cannot safely live only in a chat history.

2. How Ali’s instruction-file approach works

What did Ali mean by section files?

Prepare reviewed plain-language guidance in advance and divide it by task or business section. Resolve the trusted role and scope, load the relevant sections, and then build and validate the plan. Each specialist receives the approved instructions relevant to its task before executing it. The file names shown are proposed examples.

Keep three things distinct: instructions say how the agent should work; retrieved references support its explanation; record-specific evidence establishes what happened. If a model prediction is involved, a prepared description can explain a reason identifier, but a general guide cannot establish the cause of an individual prediction. Missing evidence must remain visible.

3. Trace Scenario 2 from question to evidence

What actually happens after a question?

Read this sequence from top to bottom. The supervisor coordinates the work; specialist workflows call scoped tools; tools retrieve records and run deterministic calculations. Results return with source identifiers so the final explanation can be checked.

In the draft, Dubai needs +486,200 and Abu Dhabi needs −74,200, producing a net +412,000. The 74,200 is an allocation change and must not be added a second time to the net discrepancy. The LLM explains the calculation returned by a tool.

4. How an agent acts without losing control

When may the agent change something?

First produce a preview of the exact proposed change. The application records approval against that payload. Before execution, the backend checks permissions and whether the data has changed. A stable operation key prevents repeated clicks or retries from submitting the same change twice.

A submission receipt is not proof that the underlying discrepancy was resolved. Read the operation status, retrieve the resulting records, and reconcile again. Both role views use the same case and event history. For GITEX, simulated future events use an explicit demo clock rather than real waiting.

5. Scenario playbooks: invoice and refund

How do invoice and refund stories use the same architecture?

For the invoice, evidence tools identify the configured discrepancy and the agent prepares correction documents for approval. For the refund, evidence arrives in stages and changes which components are supported. The same workflow building blocks handle both, with different approved instructions and tool contracts.

The refund review can finish while a supplier issue remains open. Display supported, corrected and held amounts separately. All numbers and tax treatments here belong to the synthetic draft and require domain-owner agreement before implementation.

6. Scenario playbooks: reconciliation and disclosure

Why do the return scenarios need more than a total?

Reconciliation must preserve both the net tax change and the correct Emirate allocation. Disclosure must preserve the correct period and remove the same invoices from the next draft period. A numerically plausible answer can still be wrong if either allocation is lost.

Use approved date and tax-period rules in deterministic tools. The agent gathers evidence, compares claims, explains findings and coordinates permitted actions. Alternative claims, missing replies, requests for more time and partial completion require explicit workflow branches.

7. What you build and how you prove it works

What should you implement first?

Agree data and tool contracts, then build one complete scenario from question to evidence-backed explanation. Add preview, approval, submission and verification. Reuse those contracts for the remaining scenarios and both role views.

Acceptance checks must cover arithmetic, evidence references, company boundaries, cancelled actions, duplicate submissions, stale data, missing evidence, timeouts and session reset. The sequence is a proposed implementation order; the draft email does not provide a deadline from which to promise delivery.
