How we can host our agents on Cloudera

Recommended GITEX reference path: develop in Cloudera AI Workbench, configure the multi-agent workflow in Agent Studio, publish it as a Workbench workflow endpoint, and connect our demo interface. Use an approved language-model endpoint and controlled connections to Gold and the demo backend.

The key distinction: an agent is a role, instructions, tasks and permitted tools running in our application. It is not automatically a separate server or a newly trained model. Several agents can share one workflow runtime and one LLM endpoint.

This guide assumes a Cloudera AI on Cloud reference deployment. FTA’s cloud/on-premises edition, installed release, network arrangement and licensing have not been supplied. Product capabilities below come from official documentation; placement, responsibilities and application controls are our proposed design.

Release decision to confirm: the reviewed AI Studios overview labels Studios Technical Preview and recommends test/development use. Other workflow pages describe deployment endpoints. For the POC, assess the target release with Cloudera; do not treat those deployment pages as proof of production approval.

1. Where the software runs

In the documented Agent Studio deployment, the workflow engine is a Workbench Model and the interface is a Workbench Application. Here, “Model” is the deployment object running the workflow; the language model can be a separate service. Workflow deployment documentation.

Inside our CPU workflow: the supervisor resolves the task, loads Ali’s reviewed instruction sections, builds a bounded plan and coordinates specialists. Specialist tasks call the tools for SQL, calculations, reference lookup and actions. We can package these tools with the workflow initially; a separate tool server is justified when access boundaries, reuse or independent scaling require it.

Outside the workflow: the LLM produces plans and language; the warehouse returns records; backend services persist cases and execute authorized effects. The model cannot turn a proposed adjustment into a committed business change by itself.

Security detail: a Workbench login protects access to the application, but it does not by itself implement taxpayer-level authorization. Our backend supplies trusted role/company scope and tools enforce it. With a shared service account, Ranger sees that service identity unless a supported delegation mechanism is explicitly configured. Test scoped views/policies and application authorization together. Agent Studio security recommendations; Ranger row filtering.

Prepare one versioned project

The following is a proposed code structure, not files already implemented by this diagram task:

  app.py                         # Business / Inspector UI and server adapter
  workflows/                     # Supervisor and specialist task definitions

  tests/                         # Scenario, access and action acceptance checks
  requirements.txt               # Pinned dependencies

Configure Studio: use the supported prebuilt containerized Studio runtime. The reviewed security page deprecates the old source/AMP deployment paths. Attach only the tools needed by each specialist, and configure the model endpoint through the supported provider settings. Runtime and service-account guidance; Custom tool configuration.

Publish and connect the interface: use Studio’s documented workflow publication path, then bind the custom UI’s server-side adapter to the published APIs. Start runs, retain their trace IDs and retrieve progress/results. Do not expose endpoint credentials in the visitor’s browser. The Workbench Application documentation describes project-based web app deployment and runtime port settings.

Deployment gates: check the reference arithmetic, cross-company access, injection attempts, missing evidence, stale previews, approval cancellation, repeated submissions, timeout recovery, role switching and visitor reset. Rehearse the four GITEX stories with the exact deployed release.

4. What happens when someone uses the hosted agents?

Junior-engineer walkthrough: the user asks a question in our app. The backend adds trusted company/case context. The workflow loads the approved section and asks the model for a plan. The application validates the plan and specialist tools retrieve and calculate the evidence. The model then writes an explanation from those results; output checks run before display.

For Al Yasmeen, the draft evidence supports Dubai +486,200 and Abu Dhabi −74,200, giving AED 412,000 net. An optional correction is previewed first. Approval starts the controlled action path; a backend service checks the exact payload, permissions and record freshness, then tracks and verifies the demo operation.

Human pauses: finish the explanatory run and persist a pending approval in case state. On approval, start or resume the action path using that stored state and the reviewed payload. Do not hold an in-memory worker open for days, and do not infer approval from a model-generated statement.

5. Hosting alternatives and resource planning

A. Agent Studio + Workbench — the reference POC path

Use the published workflow engine and a Workbench interface. This is the illustrated option. It suits a controlled prototype if the installed Studio release and access arrangement are acceptable. Our application still implements the case/action controls.

B. Our own code-based agent application

If Studio’s capabilities or release status do not fit, package the supervisor, specialist workflows and tools as application code. Workbench supports custom web applications. We take responsibility for the execution adapter, background work, tracing, deployment testing and durable state. Confirm the supported deployment pattern with Cloudera before selecting it for production.

C. Cloudera AI Inference Applications — a separate hosting option to assess

Current cloud documentation also describes deploying applications from Git or container images on AI Inference infrastructure, with SSO/JWT authentication options and replica controls. The app listens on 8080 and is exposed through HTTPS. The documented path requires a new AI Inference service instance for applications; do not assume an existing model-serving instance can host it. This is an alternative for a custom application, not an automatic relocation of a published Studio workflow. AI Inference Applications deployment.

What resources should we request?

  • CPU application capacity: the user interface, workflow and ordinary Python/tool execution. Start with one deployed instance of each role in the demo plan and validate concurrency. This is an initial topology, not a high-availability design.
  • Model-serving capacity: select the LLM, context length, expected concurrent requests and latency target before specifying GPUs or memory. Several agent roles can reuse one model endpoint.
  • Storage and database capacity: allow for evidence, attachments, durable cases, approval history, logs and retention. Worker RAM and temporary files are not the business record.
  • Network and readiness: verify model, SQL and backend connectivity under the actual service identity. Prewarm the demo and test the first request, not only subsequent requests.

For the cloud AI Inference route, the reviewed prerequisites specify a compute-cluster-enabled environment, a separate compute cluster, same-environment Registry and an environment-level customer-managed encryption key. Ask the platform team to validate the matching release requirements. Current cloud setup prerequisites.

6. What to agree with Cloudera before implementation

  1. Target platform: What exact Cloudera edition, release, region/site and service entitlements will host the demo?
  2. Studio status: Is the intended Agent Studio build supported for our POC and later production? What is the supported alternative if not?
  3. Hosting path: Use Workbench Application + published workflow, custom Workbench code, or AI Inference Applications? Which team owns publication and rollback?
  4. LLM endpoint: Which model and serving runtime are available? What are their tool-call, JSON, Arabic and concurrency results? Who provides capacity?
  5. Data access: Where is Gold queried? Which identity reaches Impala/Hive, and how are company scope and Inspector permissions enforced?
  6. Visitor access: Will the demo use named Workbench users, an approved kiosk session or another authenticated application path? Do not disable authentication as the access design.
  7. Backend integration: Who supplies persistent cases, approvals, demo action APIs, operation status and revalidation data?
  8. Operations: What are the timeout, concurrency, restart, backup, log-retention, reset and cold-start behaviors?

Your proposed ownership as AI engineer: workflow/task design, instruction loading, tool adapters, model integration, evidence-backed explanations and evaluation. Platform team / Cloudera: provision and support the environment, runtime, model-serving route, network and credentials. Data/backend/domain teams: reliable Gold contracts, durable state/APIs and approved tax/business meaning. Agree the split as a team.
